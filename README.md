# Walnut Technologies — Website

Frontend for **Walnut Technologies** (electronics design & manufacturing company):
a responsive, SEO-friendly React single-page application with serverless form
handling, a CMS-backed admin panel, and an automated image pipeline — deployed
on Vercel.

**Live site:** https://walnut-technologies.vercel.app

> **Note on domains.** `walnutmedical.in` is a *separate* site (Walnut Medical),
> not this build. Every canonical URL in this repo — `sitemap.xml`, `robots.txt`
> and `DEFAULT_URL` in `src/components/SEO.jsx` — points at
> `walnut-technologies.vercel.app`. If a custom domain is ever attached to this
> deployment, those three places must be updated together or search engines will
> see mismatched canonicals. `walnutmedical.in` still appears as the *contact
> email* and YouTube handle, which is correct — that's the company, not the site.

## Overview

The site covers the company's divisions (Medical, IoT, Fintech, Automotive,
Neuro), its manufacturing process, expertise, clients, resources, news and
careers.

**Content is CMS-backed.** Pages are React components, but the copy and data
(`content.json`) is published from the Walnut admin panel — see
[`walnut-admin/README.md`](walnut-admin/README.md). The build pulls fresh
content when `CMS_API_URL` is set, and otherwise falls back to the committed
`src/data/content.json`.

**The site renders without the CMS.** Content is bundled at build time, so
nothing is fetched from the API while a visitor is browsing. If the admin
backend is down, the site still loads normally — it just can't be *updated*
until it's back.

## Features

- **Multi-page SPA** — home, about (+ evolution/future detail pages), solutions
  with division showcases, process, expertise (+ detail pages), clients,
  resources, news, contact, career/apply, privacy, terms, dynamic `/p/:slug` pages
- **Responsive design** — mobile-first Tailwind UI with mobile bottom navigation
- **SEO** — per-page titles/descriptions/OG/Twitter tags via `react-helmet-async`,
  canonical URLs, `sitemap.xml`, `robots.txt`, JSON-LD structured data
- **Optimized images** — the `Picture` component serves AVIF/WebP responsive
  variants generated by the Sharp pipeline (`npm run images`)
- **CMS admin panel** — auth with MFA, media library, and content editing
  published to the site at build time (`walnut-admin/`)
- **Forms** — contact, quote, resource and job application forms POST to a
  Vercel serverless function (`api/contact.js`) that sanitizes, rate-limits and
  emails via Resend
- **Chat widget** — rule-based assistant answering from a local knowledge base
- **PWA** — service worker, web manifest, install prompt, auto-refresh on new deploys
- **Animations** — framer-motion and scroll-triggered entrance transitions
- **Security headers** — CSP, HSTS, frame-deny and cache rules in `vercel.json`

## Getting started

Prerequisites: **Node 18+** (Node 22 recommended) and **Git**.

```bash
npm install
npm run dev
```

`npm run dev` starts **three processes at once** via `concurrently`:

| Process | Port | What it is |
|---|---|---|
| site | 3001 | The Vite dev server for this website |
| admin-api | 4000 | The CMS backend (needs its own `.env`, see below) |
| admin-ui | 5174 | The CMS admin panel |

The site works on its own. The two admin processes are only needed when editing
content through the CMS.

The dev server also runs the form API locally (custom Vite plugin in
`vite.config.js`), so forms work during development once `RESEND_API_KEY` is
exported in your shell.

### Content at build time

`npm run build` runs `scripts/fetch-content.mjs` first:

| `CMS_API_URL` | Behaviour |
|---|---|
| **unset** (local dev) | Skips the fetch, keeps the committed `src/data/content.json` |
| **set** (production) | Fetches published content; retries, then falls back to the committed copy rather than failing the build or publishing empty sections |

Production sets it to `https://walnut-technologies.vercel.app/admin`. A build
therefore never hard-fails because the CMS is unreachable.

### Scripts

| Script | What it does |
|---|---|
| `npm run dev` | Site (3001) + admin API (4000) + admin UI (5174) |
| `npm run dev:site` | Just the website dev server |
| `npm run admin` | Just the CMS (API + UI) |
| `npm run build` | Fetch content → production build to `dist/` |
| `npm run fetch-content` | Pull published content into `src/data/content.json` |
| `npm run preview` | Serve the built `dist/` locally (port 4173) |
| `npm run images` | Image pipeline: optimize + responsive variants + manifest |
| `npm run optimize-images` | Convert/recompress source images → WebP |
| `npm run verify-images` | Load the built site in Chrome and flag broken images |

## Images

Every large image is re-encoded into responsive AVIF/WebP variants by
`npm run images`. **Your originals in `public/` are never modified** — the
pipeline only writes the derived `-480/-768/-1280/-1920` files.

### Encode quality

Set in `scripts/responsive-images.mjs`. AVIF at the old `quality: 55` with
4:2:0 chroma was visibly soft across the whole site, so both formats encode
higher with full-range chroma to keep logo and text edges crisp:

```js
const AVIF = { quality: 72, effort: 5, chromaSubsampling: '4:4:4' };
const WEBP = { quality: 88, effort: 6, chromaSubsampling: '4:4:4' };
```

### Cache-busting — read this before re-encoding

Variant filenames are **stable across builds**, but images are served with
`max-age=604800` (7 days). So after changing encode settings, browsers keep
showing the old bytes until their cache expires.

Fix: bump `VARIANT_VERSION` in `src/data/imageVariantVersion.js`. It's appended
as `?v=N` to every variant URL by `Picture.jsx` and the generated `preload.js`,
which changes the cache key so the new files load immediately.

```js
export const VARIANT_VERSION = '3';   // bump to '4' after re-encoding
```

After re-running the pipeline you must **delete the old variants first** — the
script skips files that already exist:

```bash
# PowerShell — remove stale variants, then rebuild
Get-ChildItem -Recurse -File public |
  Where-Object { $_.Name -match '-(480|768|1280|1920)\.(avif|webp)$' } |
  Remove-Item
npm run images
```

### Two gotchas worth remembering

- **`public/images/brand/` is cached `max-age=31536000, immutable`** — one full
  year, and `immutable` means browsers won't even revalidate. Overwriting a file
  there in place means returning visitors keep seeing the old one for a year.
  **Rename the file** so the URL changes and the cache is bypassed.
- **The brand folder is deliberately excluded** from the responsive pipeline
  (see `SKIP` in `responsive-images.mjs`), so it has no `?v=` token. Logo files
  are served as-is.

### Keeping source artwork out of the deploy

`public/` is the live web root — everything in it ships to the CDN, and anything
600px or wider is automatically turned into variants. So the **originals belong
in `design-source/`**, not `public/`. The four brand PNGs must stay PNG: the PWA
install icons and `apple-touch-icon` need PNG for Android/iOS install prompts,
and `og-cover.png` needs PNG for social scrapers that can't parse WebP.

## Quality checks

| Command | Checks |
|---|---|
| `npm run build` | Compile errors, bundle output |
| `node scripts/check-refs.mjs` | Every image path referenced in code, `content.json` and the variant manifest resolves on disk |
| `node scripts/smoke-routes.mjs` | Each route serves HTML with no error markers (`BASE=http://localhost:4173`) |
| `npm run verify-images` | Broken images / preload issues on rendered pages |
| `node scripts/check-responsive.mjs` | No horizontal overflow at 16 viewport widths |
| `node scripts/check-image-refs.mjs` | Image paths referenced but missing |

Run `check-refs.mjs` after any image or content change — it catches the
"image looks fine locally, 404s in production" class of bug in seconds.
